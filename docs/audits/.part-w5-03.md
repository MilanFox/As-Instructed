## w5-03 — Order of Operations

**Verdict:** fixed (one decision left for the user, one proposed test edit)

**Findings:**

1. **Ascending id order was a valid energisation order on every seed — the w3-01 defect, at full
   strength.** `dependencies()` builds each station's prereqs out of `['reactor', ...earlier]`,
   where `earlier` is strictly lower-indexed, for all four shapes (`mixed`, `chain`, `wide`,
   `split`). So `sub-1, sub-2, … sub-n` topologically sorted every seed. What grades order is the
   `in-order` objective (`orderedCount`, trace-based); `energised` only checks final state, which
   `power` sets unconditionally. A player writing `for (i=1..n) power('sub-'+i,'on')` passed
   `cabled`, `energised` and `in-order` on seed 1 *and* on seeds 2–4 — the level never required a
   topological sort at all, only a loop. It also earned the level's own reusable routine `waves`
   the wrong shape. Verified before the fix: id order, descending id order, alphabetical id order,
   left-to-right, top-to-bottom and fewest-prereqs-first — id order passed all four seeds.

2. **A stated mechanic that does not exist: the latch.** The `Bringing one up` fact card said
   "It only latches once every prerequisite is `on`". `Sim.power` (`src/engine/sim.ts:701`) sets
   `machine.state = state` unconditionally — there is no gate anywhere, and nothing in
   `api-bindings.ts` adds one for World 5. So a station powered before its upstream reads `on`
   immediately. A player who trusted the card and wrote the retry-until-stable loop CURRICULUM §7
   blesses — probe state, re-power what is still off — sees everything `on` after one pass, stops,
   and fails `in-order` for reasons the fact card told them were impossible. The brief's memo was
   already honest about this ("not dangerous… merely futile"); only the fact card contradicted it.

3. **The crew walk charged for calls the player was not told count.** `travelled()` sums manhattan
   legs over *every* successful `power(…, 'on')` event, so a futile call and a repeat call each add
   a leg. The fact card said only "in the order you energise them", which reads as one leg per
   station. The retry loop the curriculum tolerates therefore silently overruns `tight-order` with
   no player-facing statement of why.

4. **`in-order`'s divergence indicted a call its own predicate forgives.** `orderedCount` skips a
   futile energisation and lets a later valid one count (this is what makes the retry loop legal);
   `poweredEarly` returned on the *first* early call in the trace, even when that station was
   brought up correctly later. A retry-loop run that stranded one station was pointed at its own
   first pass instead of at the station it never got right — DESIGN §11.6 / CURRICULUM §2.6.

5. **`withinSenses` is on this level, and CURRICULUM §2 says it must not be.** §2's information
   budget note lists `w5-03` among the levels that omit it, "rationing would punish the better
   answer". `w5-03.ts:491` ships `Objectives.withinSenses('probe', 20)`, and the file's own comment
   at `w5-03.ts:25` argues for keeping it. Not a perfect-information defect — the fact card says
   `probe` is "Free, and only counted" and the star's label states the 20 — but the doc and the
   level disagree. Removing a bonus is report-instead-of-doing, so I did not touch it. See below.

6. **The `tight-order` star had zero margin and no hint anywhere near it.** `travelBudget` is
   exactly `nearestAvailableWalk`'s length — no slack, unlike `w5-05`'s deliberate 8%. All three
   hints were about topological order; nothing told the player the allowance is tight or that the
   choice that decides it is *which* of the simultaneously-ready stations you take. Title vs.
   predicate is fine — "Keep the crew walk inside the reported allowance, in steps" is exactly
   `travelled(ctx) <= vars.travelBudget`.

Things I checked and found clean: the dependency edges are fully readable (`prereq:<id>` keys named
in the facts, `probe` returns `vars`, enumeration-until-`null` stated); the disconnected-components

**Old string (exact):**

```ts
  test('in-order names which upstream was still off, and when', () => {
    const { met, divergence } = diverge(w5_03, 2, 'in-order', (sim, botId) => {
      playerApi(sim, botId, 'w5-03').power('sub-2', 'on');
    });
    expect(met).toBe(false);

      where: 'tick 0 · sub-2',
```

**New string (exact):**

```ts
  test('in-order names which upstream was still off, and when', () => {
    const second = must(machineById(w5_03.build(2), 'sub-2'), 'sub-2');
    const upstream = must(
      Object.keys(second.vars).find((key) => key.startsWith('prereq:')),
      'an upstream',
    ).slice('prereq:'.length);

    const { met, divergence } = diverge(w5_03, 2, 'in-order', (sim, botId) => {
      playerApi(sim, botId, 'w5-03').power('sub-2', 'on');
    });
    expect(met).toBe(false);
    expect(divergence).toEqual({
      where: 'tick 0 · sub-2',
      expected: `${upstream} already on`,
      received: `${upstream} was still off`,
    });
  });
```

`must` and `machineById` are already imported in that file (`machineById` is used in the
`tight-order` test below it), so no import changes are needed. With the hardcoded id it currently
reads `sub-12`; the other three w5-03 divergence tests are unaffected and were re-run by hand
against the patched level — `cabled` still gives `reactor → sub-1`, `energised` and the
never-brought-up branch still give `sub-1 · (13, 10)` / `brought up after reactor`.
